## What was built, part by part

**Part 1 — Bulk multi-transaction parsing.** `parse-transaction/index.ts` rewritten: the system prompt now instructs the model to return either a single JSON object or a JSON array depending on whether the input describes one or several transactions; the handler normalizes either shape into an array and inserts one row per parsed transaction, each carrying the full original `raw_input` verbatim and independently confidence-scored/flagged. The existing fallback (`"Could not parse model output"`, confidence 0) still fires as a single row when the model output can't be parsed at all — no manual line-splitting was added, as instructed.

**Part 2 — Rate limiting / cost ceiling infrastructure.** New `supabase/functions/_shared/rateLimit.ts`. `ENFORCE_RATE_LIMITS = false` at the top of that file — **this is the single flag controlling enforcement everywhere**, since all three parse/summary/query functions import `checkLimits` from this one shared module rather than each having their own copy. `checkLimits()` always computes real numbers (requests in the last hour, requests in the last 24h, estimated cost in the last 24h) against `request_log` and always returns them; only the `blocked` field is forced `false` while the flag is off, so the dry-run data is real and meaningful even with enforcement disabled. Every parse/summary/query request is logged to `request_log` unconditionally, on every code path including errors. The honest rejection response (`"You've reached today's limit — try again tomorrow."`, HTTP 429) is fully implemented in `limitExceededResponse()` and wired into all three functions, even though it can't fire until the flag flips.

**Part 3 — Deterministic rules layer.** `supabase/functions/_shared/categoryRules.ts` does a case-insensitive substring match of each `category_rules.pattern` against incoming `raw_input`, checked before any Groq call in `parse-transaction`. A match short-circuits parsing entirely: the row is built directly from the rule at confidence 0.95 (never below the 0.7 review threshold). New `record-correction` Edge Function persists corrections to `correction_history` and, only when the caller explicitly passes `create_rule: true` on a category correction, creates a new `category_rules` row using the transaction's exact original `raw_input` as the pattern — never a generalized fragment. **This function is not called by the frontend yet** (see "Frontend wiring" below) — see caveat below about what this means for the rules layer in practice today.

**Part 4 — Real summaries.** New `generate-summary` Edge Function. All totals (money in/out, net, top category, category breakdown) are computed in code from real `transactions` rows for the resolved date range, excluding `needs_review` rows (see reasoning below). Groq is optionally called only to phrase a nicer sentence around numbers already computed — the prompt gives it the exact formatted figures as fixed facts and instructs it not to alter them, and the response is discarded in favor of a fully deterministic fallback sentence if the model's output doesn't reproduce every required figure verbatim. No numeric aggregation is ever delegated to the model.

**Part 5 — Real data queries.** New `query-transactions` Edge Function. Groq is used only to extract structured intent (`metric`, `category`, `range`) from the question, validated against closed enum lists — any field the model returns outside those lists is discarded as `null`. The actual answer is always a real database query plus in-code arithmetic. If intent extraction fails or `metric` is null, the function returns `"I couldn't quite understand that question — try asking it differently."` rather than guessing.

**Part 6 — Audit trail.** Confirmed rather than newly built in most respects: every `transactions` insert (single free-text, bulk free-text, Excel/CSV, and rule-based match) goes through the one `parse-transaction` function and already carried full `raw_input` before this pass — Excel/CSV upload calls the same function once per row via the frontend's existing `fileToRows` + loop, so it was already covered by Part 1's fix. What Part 6 actually added: the `anon_id` column and populating it on every insert path (rule match, Groq success, Groq fallback), so every row can now be traced back to the `request_log` entries for the session that created it.

## Assumptions and defaults chosen (nothing here was fully specified in the prompt)

- **Anonymous identifier mechanism**: a header, `x-vanta-anon-id`, read by `getAnonId()` in the shared module. The frontend does not currently send this header — it would need to generate a UUID once per browser (e.g. via `crypto.randomUUID()`), store it in `localStorage`, and pass it on every call to `parseTransaction`/future endpoints. Until that frontend change happens, every row logs as `anon_id: "unknown"` — logging and rate-limit counting still work, just without per-browser granularity. This is a reasonable stand-in given auth is parked, exactly as the prompt anticipated, but it's genuinely a placeholder — `"unknown"` isn't a useful key for abuse-pattern review on its own.
- **Rate limits**: 60 requests/hour, 300/day, $1.00 estimated cost ceiling/day, all per anon_id. Conservative and arbitrary in the absence of real usage data — the explicit purpose of Part 2's unconditional logging is to replace these with real numbers once there's traffic to look at. The "day" window is a rolling 24 hours from `now()`, not a calendar day — simpler to compute correctly and avoids a hard reset-at-midnight edge case, but worth knowing if you expected calendar-day billing alignment.
- **Groq cost figures**: $0.05 / 1M input tokens, $0.08 / 1M output tokens for `llama-3.1-8b-instant`, per Groq's published rate card at the time of writing. Token counts prefer the API's own `usage` field when present, falling back to a rough `text.length / 4` estimate otherwise (a standard approximation, not exact).
- **Rule-matching conservatism**: exact case-insensitive substring match only, no normalization (no stripping punctuation, no stemming). A rule's `pattern` must appear verbatim (modulo case) inside `raw_input`. This is deliberately strict per the "keep this conservative" instruction — it will under-match rather than over-match.
- **needs_review exclusion in summaries/queries**: excluded from all totals, in both Part 4 and Part 5. Reasoning: the whole point of the confidence threshold is that a `needs_review` row's amount/direction/category haven't been confirmed as correct — including an unconfirmed guess in a number the product tells the user to trust ("you made RX this week") would undermine the trust mechanic the review flag exists to protect. `generate-summary`'s response includes `excluded_needs_review_count` so a future frontend surface could optionally say "3 more transactions still need review and aren't counted yet" if that's ever wanted.
- **`correction_history` table**: not explicitly named in the prompt, but `category_rules.source_correction_id` needs something to reference, and Part 6 asks that corrections be traceable — so this pass created a real persisted table for it. This is separate from the frontend's existing in-memory-only `src/lib/correctionHistory.ts` stub, which was left untouched (frontend changes are out of scope). They are not currently connected.

## `ENFORCE_RATE_LIMITS` — exactly where and how to turn it on

`supabase/functions/_shared/rateLimit.ts`, line 13: `export const ENFORCE_RATE_LIMITS = false;`

All three functions (`parse-transaction`, `generate-summary`, `query-transactions`) import `checkLimits` from this one file — there is no per-function copy to update. To turn enforcement on: change that one line to `true` and redeploy the shared module (Supabase bundles `_shared` into each function at deploy time, so all three functions need redeploying after the change, not just the shared file). Before flipping it, review real `request_log` data to sanity-check whether 60/hour, 300/day, and $1.00/day are still the right numbers — they were chosen with no usage data to go on.

## Confirmation: no AI-generated number anywhere

Verified by construction in both `generate-summary` and `query-transactions`:
- `query-transactions` never lets the model touch a number at all — its only job is classifying the question into a closed `{metric, category, range}` enum, validated against fixed lists; every returned figure is a real `.reduce()` over queried rows.
- `generate-summary` computes every number in `computeSummary()` before the model is ever called. If Groq is invoked, `assertNumbersPreserved()` checks that its phrased sentence contains every required figure (`total_in`, `total_out`, and `top_category_amount` when applicable) as an exact substring; if any figure is missing or altered, the model's output is discarded entirely and a deterministic, code-generated sentence is returned instead. There is no path in either function where a number reaches the response without originating from a database query.

## What minimal frontend wiring would be needed (not built — out of scope for this pass)

1. **Anonymous ID**: generate + store a UUID in `localStorage` on first load; send it as `x-vanta-anon-id` on every `supabase.functions.invoke(...)` call. Needed for Parts 2 and 6 to produce meaningful per-user data instead of everything bucketing under `"unknown"`.
2. **Summary/query placeholders**: `src/lib/routeMessage.js`-equivalent logic in the current TS chat (`App.tsx`'s message handling) currently has no summary/query intent routing at all in this rebuild — that placeholder from the old frontend wasn't ported over in the chat-only reset. Wiring Parts 4/5 up would mean adding two calls (`supabase.functions.invoke('generate-summary', ...)` and `supabase.functions.invoke('query-transactions', ...)`) somewhere in the chat send-message flow, using each function's returned `text` field directly as the bot's reply — the `total_in`/`total_out`/etc. fields are also returned if a plain-text-only UI ever wants to reformat rather than use the server's phrasing verbatim.
3. **record-correction**: the ledger's edit flow (`Ledger.tsx`, `LedgerRow.tsx`, `ReviewQueue.tsx`) currently only updates local state and logs to console. Wiring it to call `record-correction` (passing `create_rule: true` when appropriate) is what would make Part 3's rule-learning loop actually start populating `category_rules` from real corrections — without this, the table stays empty indefinitely and the rules-before-AI short-circuit in `parse-transaction` will never fire in practice, even though the matching code is fully live and ready.

## One judgment call made unprompted — flagging per your standing instruction

`parse-transaction`'s response shape changed from a single object to `{ transactions: [...] }` per Part 1. The current frontend (`src/lib/supabaseClient.ts`, untouched — frontend is out of scope) casts the raw response directly as a single `ParsedTransactionRow`, so an unmodified `{ transactions: [...] }`-only response would silently break every chat confirmation, not just bulk-paste ones. Rather than ship a backend change that breaks a currently-working frontend feature, I spread the first parsed row's fields into the top level of the response alongside `transactions`, so the existing single-transaction call site keeps working unmodified. This is a compatibility shim, not a clean design — a frontend update that reads `transactions` directly (per item 2 above) would be the right long-term fix. Flagging this explicitly since it's a deviation made to avoid a regression, not something the prompt asked for.
